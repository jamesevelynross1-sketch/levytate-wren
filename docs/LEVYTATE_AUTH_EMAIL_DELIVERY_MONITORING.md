# LevyTate authentication email delivery monitoring

## Integration state

LevyTate uses Supabase Auth with Resend custom SMTP. Supabase's SMTP response confirms that the authentication request was accepted for sending, but the current SMTP path does not return the Resend email identifier to LevyTate. Resend emits a stable Svix event ID, its email ID and (where available) the internet message ID in `email.*` webhooks. Consequently, a new Resend event is initially correlated to a LevyTate authentication request by the keyed recipient HMAC and a 30-minute window. This is explicitly recorded as `bounded`, never `exact`. Later events sharing a previously correlated provider message reference are exact.

The Resend account currently has the verified `levytate.co.uk` domain in `eu-west-1` and no delivery webhook. Supabase Auth audit records request/verification activity but does not provide recipient-mail-server delivery confirmation. Existing LevyTate audit events record request, provider acceptance/failure, identity verification, binding and sign-in without raw provider data.

## Endpoint and configuration

Provider events use:

`POST /api/levytate-auth/delivery-events/resend`

The only new application secret is `RESEND_WEBHOOK_SECRET`. It must be the endpoint signing secret generated by Resend, stored server-side for the intended environment, and must never use a `NEXT_PUBLIC_` name. Keep the existing `LEVYTATE_AUTH_RATE_LIMIT_SECRET` because recipient identifiers use the same environment-isolated HMAC-SHA256 convention.

The endpoint reads the raw body, rejects bodies over 128 KiB, and verifies `svix-id`, `svix-timestamp` and `svix-signature` using the official Svix verifier used by Resend. The verifier enforces its bounded timestamp tolerance. The database uniqueness constraint on environment, provider and Svix ID provides replay/idempotency protection. Unsigned, stale, malformed and invalidly signed requests are rejected without logging the signature or payload.

## Canonical statuses

| Resend event | LevyTate status |
| --- | --- |
| `email.sent` | `accepted` |
| `email.delivered` | `delivered` |
| `email.delivery_delayed` | `delayed` |
| `email.bounced` | `bounced` |
| `email.failed` | `failed` |
| `email.complained` | `complained` |
| `email.suppressed` | `suppressed` |
| unsupported email event | `unknown` |

`accepted` means Resend will attempt delivery; it is not delivery confirmation. Unknown events are retained as ignored evidence and are never described as delivered. The original safe provider event type is retained, but raw payloads, email content and arbitrary failure messages are not.

## Status derivation and event ordering

Immutable events are ordered by provider occurrence time and then receipt time. Complaint is the strongest terminal state. Bounce, rejection, suppression or failure supersede requested, accepted, delayed and delivered evidence. Delivered supersedes requested, accepted and delayed, but cannot erase later terminal evidence. Delayed is non-terminal. Accepted never upgrades to delivered. This logic lives in `deriveAuthenticationEmailDeliveryStatus`, not UI code.

Provider retries preserve one row per environment/provider/Svix ID. Out-of-order events remain separate and current state is re-derived from their event timestamps. The provider message reference may make later correlation exact; a single matching recipient HMAC/request within 30 minutes is bounded; ambiguous or absent matches are uncorrelated.

## Privacy, access and retention

`levytate_auth_email_delivery_events` stores only environment, provider identifiers, a request UUID, keyed recipient HMAC, canonical state, safe provider type/time, correlation confidence, bounded safe failure code and non-identifying metadata. It does not store raw email addresses, tokens, links, message bodies, credentials, cookies, learner data, employee data or full webhook payloads.

RLS is enabled and forced. Browser `public`, `anon` and `authenticated` roles receive no table or cleanup-function access. Only the service role can access delivery evidence. Read contracts return status/count/time/confidence/environment/safe-reason data without recipient hashes. Detailed events expire after 90 days and `levytate_cleanup_auth_email_delivery_events` deletes expired rows in bounded batches.

Resend `Permanent` bounce, rejection, complaint and suppression evidence prevents repeated automatic authentication sends for the affected keyed recipient during retained evidence. `Transient` and `Undetermined` bounces remain operational evidence but do not activate this local suppression boundary. It does not delete Auth identities, memberships, organisations or roles. There is no automatic retry or background resend. The normal sign-in flow remains generic and subject to distributed limits.

## Failure behaviour

- Resend accepted but delayed: retain `accepted` and `delayed`; do not resend automatically.
- Resend rejected or failed: retain a safe terminal status; keep the public response generic.
- Webhook delayed: provider occurrence time preserves ordering when it eventually arrives.
- Endpoint unavailable: Resend may retry; uniqueness makes the retry idempotent.
- Duplicate event: return success and do not add another row.
- Evidence storage unavailable: return a bounded 503 to Resend; do not expose provider/database detail. Authentication email requests remain enumeration resistant and the monitoring store does not replace Supabase verification.

## Protected Preview and production cutover

Vercel Authentication protects all Preview requests, including third-party webhooks. Do not remove it. A live Preview callback requires Vercel's Protection Bypass for Automation: create a dedicated revocable secret, place its query parameter only in the Resend Preview webhook URL, and set the Preview `RESEND_WEBHOOK_SECRET`. Do not reuse that URL or secret for Production. Until both are configured, validation is limited to officially signed fixtures against the endpoint and live Supabase persistence.

For Sprint 2C, configure a separate Production Resend webhook pointing to the final LevyTate production endpoint, set a Production-only `RESEND_WEBHOOK_SECRET`, subscribe only to `email.sent`, `email.delivered`, `email.delivery_delayed`, `email.bounced`, `email.failed`, `email.complained` and `email.suppressed`, then perform one controlled non-prospect test. This does not change the authentication callback domain.

To rotate a signing secret, create or rotate the endpoint in Resend, update only the matching Vercel environment secret, deploy that environment, verify one signed event, and revoke the previous endpoint/secret. Never print either secret.

## Safe testing

Use `node scripts/validate-auth-email-delivery-monitoring.mjs` for schema, privacy, mapping and status rules. After applying migration 022 to the exact approved Supabase project, run `node scripts/validate-auth-email-delivery-monitoring-live.mjs` while a local server is running with a temporary local webhook secret. It creates signed synthetic provider events for an HMAC-only fictional recipient, checks retry/order/privacy/cleanup/RLS, and removes its rows. It sends no email and creates no Auth user or employer membership.

## Isolated rollback

Migration 022 is additive and does not alter existing rows, indexes, policies or employer-domain objects. If rollback is required before the monitoring endpoint is activated, first disable the corresponding Resend webhook, then drop `public.levytate_cleanup_auth_email_delivery_events(integer, timestamptz)` and `public.levytate_auth_email_delivery_events`. This removes delivery evidence only. Do not roll back by changing users, memberships, authentication bindings, rate-limit storage or employer data.

Sprint 2B.2B2 should add Platform Admin-only read presentation for delivery health, recent terminal failures, provider state and correlation confidence. It must not expose recipient hashes, provider payloads, credentials or resend controls.
